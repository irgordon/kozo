# KOZO v1.0.0 Documentation Audit

## Purpose

This audit checks whether KOZO's post-publication documentation helps users,
maintainers, and engineers understand the released product without overstating
its capability. It reviews current entry points and preserves historical
release records.

## Current Strengths

- Current pages already identified `v1.0.0` as the final release.
- Product limits were explicit and did not claim a desktop, shell, scheduler,
  general userspace, compatibility, stable public ABI, or production readiness.
- Engineering pages linked to authoritative documents instead of redefining
  exact contract geometry.
- The prior v0.8.9 audit established a useful wiki foundation.

## Incorrect or Stale Statements

- The wiki landing page labeled the RC status page as current.
- The downloaded-ISO command did not set the portable QEMU binary override.
- QEMU timeout `124` was not explained, leaving room to confuse a governed
  terminal halt with an arbitrary timeout.

No current page incorrectly described `main` as the `v1.0.0` tag target.

## Missing User Information

- A numbered release-first path using only published assets.
- A stop rule for checksum mismatch.
- A short representative success suffix.
- An explanation that KOZO is non-interactive.
- A precise condition under which timeout `124` accompanies success.
- Safe experiments and a clear next-reading path.

## Missing Maintainer Information

- Separate runtime-change and documentation-only workflows.
- The relationship among the immutable `v1.0.0` tag, current `main`, and
  immutable `v1.0.0-rc.1`.
- An explicit patch-release rule for product corrections.
- A warning policy that keeps non-blocking and local-tool findings visible.

## Missing Engineering Information

- One complete top-down runtime sequence.
- A source map from each mechanism to its implementation.
- Consolidated explanations of the memory, privilege, capability, evidence,
  and fail-closed models.
- A direct statement that fixed fault sinks are not exception recovery or
  hostile-code containment.

## Duplicated Content

The prior wiki repeated release status and current capability in several page
openings. The revised landing page owns navigation and release identity. Each
other page starts with its audience-specific purpose and links back when needed.

Exact marker order, selector values, memory geometry, and response layouts
remain in contracts and authoritative engineering documents rather than being
copied into the wiki.

## Terminology Findings

The existing terms were accurate, but the table required users to start with
engineering vocabulary. The revision puts plain wording first and adds release
artifact, annotated tag, and application binary interface terms. It explains
that KOZO has no stable public ABI.

## Navigation Findings

The previous landing page offered a flat list and one reading order. The new
table routes readers by intent. The root README now uses the same paths without
duplicating their content.

## Capability-Claim Review

Confirmed v1.0.0 claims include bootable x86-64 QEMU ISO, controlled stack and
memory initialization, x87/SSE state, fixed four-level paging, fixed user
mappings, GDT/TSS/IDT setup, one Ring 3 round trip, fixed copy-in/copy-out and
status response, a three-iteration Odin loop, two internal capabilities,
ordered evidence, and terminal halt.

The revised pages continue to exclude desktop, shell, scheduler, persistent
processes, general userspace, general syscalls, filesystem, drivers, networking,
dynamic virtual memory, executable loading, compatibility, hostile-code
containment, stable public ABI, and production readiness.

## Changes Made

- Routed the wiki through three distinct audience paths.
- Made the hosted ISO the first user action.
- Added exact checksum, QEMU, timeout, and success guidance.
- Expanded safe maintenance and patch-release rules.
- Added a top-down engineering sequence and source map.
- Expanded real troubleshooting and plain-language terminology.
- Aligned README, roadmap, phase map, changelog, and governed task state.

## Historical Documents Retained

The approved `docs/releases/v1.0.0.md`, final evidence, RC notes, RC status,
RC evidence, earlier changelog entries, prior audit, and historical task
records remain unchanged. Historical statements continue to describe their
named phase rather than the current tree.

## Validation Performed

- Live GitHub readback confirmed that `v1.0.0` remains a final, non-draft
  release with six assets and that `v1.0.0-rc.1` remains a non-draft
  prerelease.
- A focused scan checked 72 local links across the root README, all wiki pages,
  and this audit; no local target was missing.
- All six final-release assets were downloaded into a clean directory, and
  every entry in `SHA256SUMS` passed.
- The downloaded `kozo.iso` produced QEMU outcome `pass`, no blocker, all 41
  ordered markers, and final marker `KOZO_RUNTIME_RETURN_OK`. QEMU exit `124`
  occurred only after the governed terminal halt was proven.
- A clean clone at audit baseline
  `fad5f5305299a7b9ff7a63df5b1fbeaa021dd7f7` passed Odin and Cargo checks,
  built the boot image, and reproduced the 41-marker QEMU result.
- Python discovery passed 1,050 tests. Odin, Cargo, cargo-deny, and cargo-audit
  passed. Cargo retained four documented generated-ABI warnings.
- Governed verification passed 67 checks with no failures, QEMU outcome
  `pass`, no blocker, and all 41 markers.
- Diff checks found no runtime, userspace, harness, schema, contract, or script
  change and no inappropriate local absolute path in the committed
  documentation.

## Remaining Documentation Debt

- Detailed historical engineering documents remain dense by design; the wiki
  now provides the shorter entry path.
- External URL availability remains a live network concern and is not made
  repository authority.
- A future feature or patch release must update only the pages materially
  affected by its proven behavior.

## Conclusion

The revised wiki describes the released kernel foundation rather than an
aspirational operating system. Users can run and recognize it, maintainers can
change it without weakening release history, and engineers can trace the
complete path to authoritative implementation and evidence.
